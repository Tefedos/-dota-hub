# Draft Analyzer v1.1.1

Внутренний Python-модуль анализирует возможности героев и доступную при выборе информацию. Он не использует результат матча, KDA, счёт, предметы, длительность, фарм или наблюдаемые после игры роли. Баллы — объяснимая, пока не откалиброванная гипотеза полезности. Это не прогноз winrate и не оценка человека, нажавшего pick.

## Вызов и контракт

```python
from app.services.draft.analyzer import analyze_draft

report = analyze_draft(normalized_match)  # deterministic, no I/O
payload = report.model_dump(mode="json")
```

Для явного получения статистики используйте `analyze_with_matchups(normalized_match, provider)`, где `provider = OpenDotaMatchups(open_dota_client)`. Существующий `OpenDotaClient` создаётся с настройками проекта; вызывающий код закрывает его через `await client.close()`. Не более десяти различных hero IDs запрашиваются последовательно, при 429 сбор прекращается. Групповой бот и локальный Alpha-сервис вызывают этот путь при новом расчёте и сохраняют итоговый отчёт. Если отчёт уже сохранён с тем же исходным матчем и версией конфигурации, используется сохранённый отчёт, без нового сетевого запроса.

`DraftReport` содержит строковый match_id, patch, SEQUENTIAL/FINAL_ONLY, политику видимости, диагностические коды, исходные действия, pick_events, обе команды, draft_advantage, model_version, SHA-256 конфигурации и статистических входов, покрытие и ограничения. Строгие Pydantic DTO находятся в `app/models/draft.py`. Порядок полей и сериализация детерминированы.

Для каждого героя: `at_pick` и `final_context` имеют собственные score, confidence, grade, axes, evidence_coverage и reasons. Удобные `at_pick_score/final_score` повторяют значения этих объектов. `hero_name` берётся из версионированного каталога и может быть `null` для неизвестного ID. `pros/cons` содержат до двух подтверждённых для конкретного патча индивидуальных или парных фраз каждого знака; командные функции в них не копируются. `Reason.scope` различает `individual`, `interaction`, `team`, `data`; при чтении старого сохранённого JSON без поля применяется значение `data`. Полный список reason codes/evidence/source_refs остаётся в оценке. Неизвестному герою не приписывается порядковый номер выбора.

## Порядок и видимость

Проверяются все действия, уникальные и непрерывные order, source_order, допустимость pick/ban, состав 5+5, уникальные герои, точное соответствие `(team, hero)` пиков финальному roster. Повторяющиеся баны или одновременный ban/pick одного героя отвергают последовательность. Финальные составы при этом остаются доступны.

Уникальные order сортируются, даже если массив пришёл переставленным; исходный source_order сохраняется. Дубликаты, gaps, частичный список или несовпадение roster приводят к FINAL_ONLY. Ни at_pick, ни stage, ни последующий контрпик в этом режиме не объявляются. Баны остаются в `actions`.

Политика выбирается только по точной паре `(game_mode, patch)` из проверенного registry:

- `hidden_221`: первые два выбора каждой команды — раунд 1, следующие два — раунд 2, последний — раунд 3. Порядок не должен пересекать границы раундов; все баны должны предшествовать пикам. Свои предыдущие пики известны, враги того же раунда скрыты даже при меньшем order. Будущие личности не попадают в `PickVisibility`: `enemy_hidden_or_unknown` содержит только количество.
- `public_sequence`: отдельная явно подтверждённая политика публичной последовательности; предыдущие пики и баны известны, stage остаётся null. Номера стадий Captains Mode не реконструируются.

**Проверенная production-политика v1 ограничена историческим Ranked All Pick: game_mode=22, patch=46 (7.27).** Valve описывает переход к 2/2/1; OpenDota constants связывают имена режимов/патчей с ID. Это не доказательство неизменности правил для любого последующего патча. Современные patch IDs и Captains Mode по умолчанию используют FINAL_ONLY. Registry расширяется после документированной проверки; тестовый registry для patch=60 явно помечен `fixture://`, в production defaults его нет.

Источники: [Valve 7.27](https://www.dota2.com/patches/7.27), [OpenDota game_mode](https://raw.githubusercontent.com/odota/dotaconstants/master/build/game_mode.json), [OpenDota patch IDs](https://raw.githubusercontent.com/odota/dotaconstants/master/build/patch.json).

В текущих defaults нет пересечения патчей механических профилей (60) и политики последовательности (46). Более того, качественные профили patch=60 пока не имеют доказанной **численной** применимости именно к историческому патчу 60. Поэтому численные at_pick в SEQUENTIAL проверены только на явно тестовой конфигурации. Для production patch=46 доступны проверенные представления видимости, но численные оценки null; для patch=60 описательные механические причины возможны с `snapshot_unverified`, но они не начисляют баллы. Финальная численная оценка допустима только при достаточном количестве подтверждённых осей, например после будущей верификации конкретных версий правил. Это существенный пробел для полноценного анализа современных игр.

## Rules v1

Версия правила, код причины, применимость к patch, источники, имена способностей и capability tags задают объяснимое основание. Numeric utility — гипотеза проекта, а не измеренная сила пары. `patches` ограничивает качественное применение правила, а `verified_numeric_patches` отдельно разрешает его численный вклад. Численное правило требует подтверждения patch ID для обоих профилей и самого правила. Production defaults сейчас оставляют `verified_numeric_patches` пустым; ссылка на изменяемую ветку `master` и текущая страница Valve историческую применимость к patch ID 60 не подтверждают. Тестовые конфигурации используют явно маркированные `fixture://` источники.

Начальный набор качественных профилей ограничен Oracle, Hoodwink, Chaos Knight, Death Prophet, Spectre, Earthshaker, Anti-Mage, Crystal Maiden, Lina, Tidehunter и Shadow Shaman для patch ID 60 (семейство 7.41). Справочник не скачивается при анализе и не распространяется на неизвестные patch IDs. Источники профиля: официальная страница героя Valve и публичный [набор abilities OpenDota](https://raw.githubusercontent.com/odota/dotaconstants/master/build/abilities.json). Значения урона, facet и subpatch не моделируются; наличие capability — качественная интерпретация базовых способностей, а не сертификация полного билда на 7.41x. Теги farm/midgame/lategame — экспертные предположения проекта с низкой уверенностью.

Отдельно включён справочник **127 героев**: имена, опубликованные роли и тип атаки. Он зафиксирован по [commit 5c0242d OpenDota](https://raw.githubusercontent.com/odota/dotaconstants/5c0242df9057848fa2036ca3fafe9f2bd4508163/build/heroes.json) в `app/data/hero_catalog.json`. `HeroDescriptor` не равен механическому `HeroProfile`. Эти признаки возвращаются как нейтральная причина `catalog_hero_features`, с `patch_applicability=snapshot_unverified`. Carry/Support не означают подтверждённую позицию; Nuker не означает магический урон, Pusher не доказывает конкретную способность. Поэтому эти метки не преобразуются в численные оси или механические контрпики. Это расширяет проверяемую описательную информацию, но не выдаёт 127 героев за полное численное покрытие. Версия справочника входит в config_digest.

Правила взаимодействий:

| Код | Основание | Utility v1 |
| --- | --- | --- |
| save_sustained | Союзный сейв даёт окно для продолжительного воздействия | 75 |
| control_followup | Контроль помогает применить магический урон союзника | 65 |
| initiation_aoe | Инициация создаёт возможность массового урона | 75 |
| aoe_illusions | Массовый урон действует по группе иллюзий; расположение и защита важны | 70 для источника, 30 для цели |

Это общие взаимодействия tags, а не жёсткие списки «плохих пиков». Для Earthshaker/CK причиной служат Echo Slam и Phantasm: дополнительные юниты создают возможность для массового воздействия, но численная сила не выводится из этой механики. По умолчанию все механические причины помечены low confidence и `snapshot_unverified`; `exact_patch:N` допустим только с отдельным подтверждением. Симметричное правило (`directionality=symmetric`) учитывается один раз на каноническую неупорядоченную пару и код правила. Направленное правило (`directed`) сохраняет порядок actor/target, поэтому два разных направления могут дать два основания. В обеих ветках повтор того же факта по той же паре и коду в одну ось не добавляется. Matchup statistics хранятся отдельно от причинного объяснения.

Командные функции рассматриваются по всему составу: инициация вместе с контролем, физический вместе с магическим уроном, возможности midgame, lategame и давления на строения. Utility 75 — модельная гипотеза для **подтверждённого для патча** присутствия функции, а не запасное значение. Число 25 для предполагаемого отсутствия функции сейчас не применяется: отсутствие tag, даже у всех профилей, не доказывает отсутствие способности в игре. Без положительного подтверждения соответствующая ось `null`; при качественном, но не численно верифицированном подтверждении вывод остаётся описательным. Командные причины находятся в `TeamDraftScore`; персональные карточки не наследуют их автоматически. Сейв/диспел/мобильность дополнительно объясняются словами.

При двух героях с тегом farm выводится условное командное предупреждение с ID именно этой пары; оно появляется в карточках только участвующих героев как `resource_warnings`, без записи в их `cons`. Позиции 1–5 не выводятся из героя или lane_role. Поэтому `laning` и `farm_economy` численно null; ролевая оценка остаётся ограничением, а не выдуманной цифрой. Ни один итог не заявляет сильную линию без достаточных данных.

## Матчапы OpenDota

Источник: `GET /heroes/{hero_id}/matchups` из [официальной OpenAPI-схемы](https://api.opendota.com/api). Используются hero_id, games_played и wins. Response не гарантирует фильтрацию по патчу/позиции/рангу/периоду. Каждая строка содержит fetched_at, source_ref и `patch_scope=aggregate_unknown`.

Учитываются только строки с `games_played >= 100`. Сглаженный процент: `100 * (wins + 200/2) / (games_played + 200)`. При малой выборке score отсутствует, 50 не подставляется. Нулевые игры, отрицательные/нецелые счётчики, wins > games, дубли и hero=self валидируются; некорректный batch не используется.

Процент — корреляционный сигнал, confidence low. Он никогда сам по себе не создаёт `countered_heroes/threatened_by_heroes`: эти списки требуют механического правила. Для пары усредняются только реально доступные сглаженный сигнал и применимые механические utility; обратная статистика другого героя не изобретается. Матчап-ось требует поддержки каждой пары текущего контекста. Неизвестные пары не считаются равными 50.

Транспорт общий с ingestion №05: timeout и bounded retry на сетевых ошибках/5xx, 404/429 не повторяются. API key остаётся в Authorization header. Кэш живёт в памяти provider: успешные данные 3600 с, ошибки 60 с; 429 задаёт общий для героев cooldown по Retry-After. Одновременные запросы одного hero ID объединяются. После перезапуска статистику надо получить повторно либо передать сохранённый batch. Сам рассчитанный DraftReport хранится в существующем хранилище анализов вместе с `evidence_digest`; отдельного постоянного хранилища для сырых matchup batches пока нет.

## Веса и достаточность

| Ось | Вес | Основание |
| --- | --- | --- |
| matchup | 0.30 | Поддержанные пары текущего героя/команды с известными врагами |
| synergy | 0.25 | Применимые взаимодействия союзников |
| balance | 0.20 | Инициация/контроль и сочетание типов урона |
| phase | 0.15 | Подтверждённые справочником функции midgame/lategame |
| win_condition | 0.10 | Сочетание давления на объекты и позднего потенциала |

Условия score: герой и союзный контекст покрыты, минимум две оси и минимум 0.55 исходного веса. Доступные веса перенормируются по формуле `sum(weight_i * axis_i) / sum(weight_i)` только для подтверждённых осей; `evidence_coverage` показывает долю исходного веса. В личном контексте `balance`, `phase`, `win_condition` не заимствуются у команды и равны `null`; возможны только личные `matchup` и парные `synergy`. Ранний пик без матчапов/синергии получит `null`. Никакие неизвестные оси не дополняются 50, 65, 75 или иным нейтральным баллом. При вычисленном балле и неполном покрытии добавляется `partial_evidence`. Coverage ниже 0.70, агрегатная статистика неизвестного патча или непроверенные описательные причины дают low confidence; выше — максимум medium, high для численной эвристики v1 не используется.

Grade boundaries в config: <35 неудачный, <50 спорный, <70 средний, >=70 хороший. Это категории оценки контекста, не обвинение игрока. При null grade тоже null, confidence low и reason `insufficient_data` с текстом «Нет оснований для уверенной оценки».

Командная оценка рассчитывается заново по всем взаимодействиям и функциям команды, а не средним пяти player scores. Breakdown содержит synergy, counters, laning, initiation_control, damage_mix, farm_economy, midgame, lategame, objectives. Преимущество сравнивается только для полных составов с численными оценками и одинаковым набором поддержанных осей. Разница до 5 баллов — approximately_even. Иначе Radiant/Dire; недостаточные основания — insufficient_data.

## Поздние изменения

at_pick видит только разрешённых политикой союзников и врагов. Итог использует полные составы. Общий post_pick_delta может включать поздних союзников, соперников и изменение покрытия — это не причинная атрибуция.

Для каждого **действительно последующего** пика соперника вычисляется отдельное влияние: финальная оценка минус контрфактическая финальная оценка без этого соперника, все остальные входы фиксированы. Если одну оценку получить нельзя, delta=null, аргументы сохраняются. Одновременный скрытый раунд не считается поздним контрпиком, даже если source order больше. Плохой order отключает всю историческую интерпретацию.

## Воспроизводимость и интеграция

Для воспроизведения нужны normalized snapshot, exact config с model_version, тот же snapshot матчапов и версия кода. SHA-256 конфигурации и статистики присутствуют в отчёте. Время генерации и случайность не используются. Перестановка статистических batches нормализуется. Исходные объекты не меняются.

Новых HTTP endpoints и таблиц нет. Групповой сценарий `/match` и локальный Alpha используют прежнюю сущность анализа; обновлённый `config_digest`/`model_version` заставляет пересчитать старый отчёт при новом запуске анализа. Данные внешнего провайдера остаются агрегатами неизвестного патча и не доказывают историческую силу конкретной способности.

## Универсальность и реальные данные

Ядро не ветвится по Match ID, названию героя или составу из десяти ID. Идентификаторы конкретных героев находятся в справочниках; вычисления используют входные составы, признаки и конфигурацию. Доменная константа 5+5 относится к формату команды. Это не поддержка нестандартных режимов с иным числом игроков.

Независимая фикстура содержит Axe, Bane, Drow Ranger, Juggernaut, Mirana, Sven, Zeus, Lion, Leshrac и Lifestealer. В production defaults ей доступны дескрипторы и внешние матчапы, а итоговые баллы null из-за отсутствия проверенных механических профилей. Отдельные тестовые профили с `fixture://` проверяют расширяемость алгоритма; их намеренно условные признаки не являются утверждениями о реальных способностях этих героев. Полная перенумерация ID одновременно во входе и конфигурации сохраняет оценки. Перестановка состава или изменение весов правил может изменить оценки. Замена Match ID, исхода и KDA не меняет расчёт.

`scripts/audit_draft.py` сохраняет минимальный снимок без личностей игроков и chat, статистические batches и полный отчёт. `--offline` воспроизводит его без сети. Live-запуск обновляет данные, поэтому для нового smoke следует выбрать отдельный output-dir, сохраняя регрессионную фикстуру неизменной.

На реальном матче 9051271323 получены 16 действий: 11 pick и 5 ban. Дополнительный pick Pudge отсутствует в финальном roster. Последовательность отвергается без удаления действия, все десять финальных героев остаются в отчёте. Исторические числа из [отчёта 07A](STAGE2_07A_REPORT.md) относятся к версии v1 до Alpha-исправлений; актуальные ограничения и результаты приведены в [отчёте 07A.1](STAGE2_07A1_ALPHA_BUGFIX_REPORT.md).
