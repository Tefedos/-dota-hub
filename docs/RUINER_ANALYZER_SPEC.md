# Ruiner Analyzer — ruiner_v1

Внутренний `RoleAwarePerformanceEvaluator` оценивает относительные признаки проблемного исполнения, независимо для Radiant и Dire. Индекс 0 означает меньше обнаруженных признаков относительно сравниваемых союзников, 100 — больше. Он не является вероятностью виновности, объективной оценкой качества игры или доказательством причин поражения. Равные показатели всей команды дают нулевые относительные отклонения даже тогда, когда вся команда могла сыграть плохо.

## Контракт и границы

```python
from app.services.performance import analyze_performance

report = analyze_performance(normalized_match)
payload = report.model_dump(mode="json")
```

`RuinerReport`: match_id, model_version, config_digest, quality, обе teams, все доступные players и summary. Время вычисления и случайность не участвуют; одинаковые входы и конфигурация дают одинаковый JSON. `config_digest` — SHA-256 сериализованной конфигурации.

Игрок: player_slot, team_player_number, hero_id, team, отдельная позиция исполнения, role_group, error_index, confidence, evidence_coverage, axes, observed_metrics, positive_credit, positive_signals, negative_signals, missing_metrics, reason_codes, limitations. Имена пользователей и Steam IDs в отчёт не входят.

Каждый signal содержит код, русскую фразу, metric, наблюдаемое value, фактическую reference, comparison_slots, magnitude и источник. Полные значения наблюдений сохраняются в observed_metrics; значения для объяснений округляются до четырёх знаков. `missing_metrics` включает также производные метрики, которые нельзя корректно вычислить из присутствующих исходных полей, например KDA при нуле смертей.

TeamPerformanceReport сообщает свою команду, слоты, число рассчитанных индексов, threshold, minimum_margin и собственный selection. Общий summary без явного `selected_team` всегда `no_confident_selection`, evidence=`team_context_not_provided`; команда пользователя не угадывается по победителю, Telegram-группе или первому элементу массива.

Сервис не принимает DraftReport и не импортирует Draft Analyzer. Он не использует winner, picks_bans, голд-advantage, match outcome или внешнюю оценку драфта. Из командного счёта используется только число убийств для участия в них. Ни один коэффициент не выбирается по Match ID или hero ID.

## Позиции и аддитивное расширение №06

Существующий `PlayerStat.position` описывает линию. Его `lane_role=1` не означает фармовую позицию 1: на одной линии играют и core, и support. Старое поле и его контракт сохранены.

Добавлен `PlayerStat.performance_position: FarmPositionEvidence`:

- position: 1–5 или null;
- evidence: confirmed / estimated / unknown;
- source_field: источник либо null.

OpenDota `position_est` нормализуется только как **estimated**. Его описание прямо говорит об оценке из раннего фарма и данных линии. Входные произвольные `position`/`role` не становятся подтверждением. Если `position_est` отсутствует или невалиден, позиция unknown. Оценочная роль может влиять на выбор ролевой группы, но confidence остаётся low, выбор игрока запрещён. Это ограничение особенно существенно, поскольку оценка роли из фарма сама может ошибочно классифицировать игрока с плохой экономикой.

Внутренний вызывающий код может передать `positions={player_slot: FarmPositionEvidence(...)}` с проверенным источником назначения ролей. Это доверенный внутренний аргумент, не новый клиентский API. Для confirmed нужны номер и source_field. Несуществующий player_slot отклоняется; повтор позиции внутри команды вызывает fallback этой команды в unknown с `conflicting_positions`. Текущий бот не придумывает и не передаёт confirmed-позиции.

Ролевые группы: позиции 1–3 — core, 4–5 — support. При unknown используется общий командный fallback. Неизвестная позиция не выводится из героя, GPM или lane_role. Старое summary.data_quality.roles относится к прежним данным линии и не используется для уверенности Ruiner Analyzer.

Добавлены nullable-счётчики obs_placed, sen_placed, observer_kills, sentry_kills и соответствующие available_fields. Ноль сохраняется; отсутствие, bool, дробь, отрицательное или чрезмерное число становится null. Прежние DTO совместимы за счёт значений по умолчанию. Схема БД и snapshot ingestion v1 не меняются: исходные поля уже сохранялись в raw payload.

Источник определений: [OpenDota OpenAPI](https://api.opendota.com/api), `MatchResponse.players`: position_est, obs_placed, sen_placed, observer_kills, sentry_kills. Счётчики использования/покупки вардов не подменяют установленные или уничтоженные варды.

## Наблюдения и baseline

Никакой проверенной популяционной выборки по герою, позиции, патчу и рейтингу в проекте нет. Поэтому здесь нет заявлений «норма core — 600 GPM» или «норма support — N смертей». Фактический baseline каждой метрики — **медиана значений других сравниваемых игроков своей команды**, исключая самого оцениваемого игрока.

При известной/оценочной позиции сравниваются другие core либо другие support. При unknown сравниваются все остальные союзники с низкой уверенностью. Для сравнения нужно не менее двух доступных наблюдений вместе с самим игроком; у support это часто только один другой игрок. Такая маленькая группа — ограничение эвристики, не статистически значимая выборка. Пропуски среди peers не заменяются нулями; реальные comparison_slots видны в каждом аргументе.

Наблюдаемые метрики:

| Метрика | Расчёт / обработка |
| --- | --- |
| deaths_per_min | deaths / (duration / 60) |
| kill_participation | (kills + assists) / team_score, только при team_score ≥ 10 и 0 ≤ kills + assists ≤ team_score |
| kda | (kills + assists) / deaths; при deaths=0 — null с отдельной причиной |
| gpm, xpm | Нормализованные значения OpenDota |
| hero_damage_per_min, tower_damage_per_min, healing_per_min | Соответствующий total / минуты матча |
| obs_placed, sen_placed, observer_kills, sentry_kills | Наблюдаемые счётчики; в одном матче длительность общая |

KDA показан как описательная метрика. Он не добавляет третий штраф за те же смерти/низкое участие. Last hits, net worth и прочие коррелированные накопительные показатели не получают дополнительных весов поверх GPM/XPM в v1. Контекст смерти, ценность конкретного лечения, удачность placement вардов и доступность целей не восстанавливаются из totals.

Длительность используется для rates и ограничения коротких матчей. При сравнении игроков одного матча общий временной множитель математически сокращается: модель не выдаёт межматчевую «норму смертности по длительности» без проверенного внешнего baseline.

## Формула

Все коэффициенты и пороги находятся в `PerformanceConfig`, model_version=`ruiner_v1`. Они являются гипотезами дизайна и ограничителями достаточности данных, не результатом обучения и не измеренными нормами.

Пусть `x` — значение игрока, `b` — медиана peers, `u` — минимальная единица знаменателя. Для счётчиков/GPM/XPM `u=1`; для метрики в минуту `u=1/minutes`; для участия `u=1/team_score`. Это единица наблюдения, не предположение о нормальном исполнении.

```text
denominator = max(b, u)
survival_deficit = clamp((x - b) / denominator, 0, 1)
other_deficit   = clamp((b - x) / denominator, 0, 1)
positive_gain  = clamp((x - b) / denominator, 0, 1)
```

Для метрик, где больше лучше, при b=0 численная сравнительная ось/credit отсутствует. Если x>0, остаётся описательная причина observed_contribution. Например, единица лечения на фоне нулевого лечения peers не создаёт автоматически максимальный бонус. При нулевой медиане смертности применяется floor, но survival вообще доступен только при известных смертях всех пяти союзников и их сумме ≥5.

Для core:

| Ось | Содержание | Вес |
| --- | --- | --- |
| survival | Относительный избыток смертности | 0.30 |
| participation | Относительный недостаток участия в убийствах | 0.25 |
| economy | Среднее дефицитов GPM и XPM; нужны обе метрики | 0.25 |
| impact | Относительный недостаток hero damage/min | 0.20 |

Для support и unknown используются survival 0.50 и participation 0.50. Низкие GPM/XPM и damage не штрафуются: профиль героя и подтверждённая обязанность наносить урон неизвестны. Для support роль определяет cohort; при unknown cohort смешанный и confidence low.

Вклад в строения, лечение, установку/уничтожение вардов — положительные сигналы без универсального штрафа за ноль. Для support/unknown сюда относится и hero damage. Из доступных positive_gain берётся **максимум**, а не сумма; коррелированные ward counters не дают несколько накопленных бонусов. Credit = 15 × max(positive_gain), в пределах 0–15. Если сравнительного положительного свидетельства нет, credit=0; отсутствие optional-поля не становится отрицательным signal. Малые различия и важность вклада остаются ограничением этого неоткалиброванного бонуса.

```text
coverage = сумма исходных весов доступных осей
burden = 100 × сумма(weight × deficit) / coverage
error_index = round_half_up(max(0, burden - positive_credit))
```

Требуется минимум две доступные оси и coverage ≥0.70. Недоступные оси не получают штрафа 0/50/100; доступные веса перенормируются. Значение 0 означает отсутствие относительных отрицательных отклонений на доступных осях с учётом credit, а не доказательство идеальной игры.

Отрицательные/положительные сравнения получают текстовый signal при magnitude ≥0.20. Меньшие отклонения остаются в axes и могут влиять на индекс. Избыточная смертность ограничена единицей внутри оси: 50 смертей при прочих нормальных данных не создают индекс 100 и не проходят критерий двух независимых отрицательных осей.

## Достаточность и выбор игрока

Поддержаны game_mode 1 (All Pick), 2 (Captains Mode), 22 (All Draft/Ranked All Pick). Turbo и другие/неизвестные modes по умолчанию unscored. Это ограничение области применения модели, не режимная политика видимости драфта.

До расчёта нужны duration ≥900 секунд, команда из пяти доступных игроков с корректной стороной слотов, известными и различными hero IDs. Нет подходящего режима, длительности, roster или достаточно осей → index=null, confidence=low. Каждому доступному игроку отчёт всё равно создаётся; отсутствующие игроки не выдумываются.

Confidence medium означает полноту входа для выбранной относительной эвристики: индекс рассчитан, coverage=1, позиции игрока и его сравниваемой ролевой группы confirmed. В остальных случаях confidence low. Это не статистическая уверенность в причинности. `quality=sufficient` — десять medium-оценок, `partial` — есть хотя бы один индекс, иначе `insufficient`.

В каждой команде выбор возможен, только если:

1. Все пять игроков имеют индексы, medium confidence и coverage=1.
2. Максимальный индекс ≥70.
3. Его отрыв от второго ≥15; равенство и меньший разрыв не разрешают произвольный выбор по слоту.
4. Не менее двух осей выбранного игрока имеют deficit ≥0.20.

Границы включительны. Порог 70 и отрыв 15 — конфигурационные гипотезы v1. Не выполнено условие → `no_confident_selection` с причиной. Даже selected означает наиболее выраженную совокупность доступных относительных сигналов в данной команде, а не установленного виновника.

## Интеграция

`JobService._run` после успешного FOUND_FULL/FOUND_PARTIAL и при наличии snapshot вызывает существующий normalizer и единый `analyze_performance`. Match ID повторно сверяется. `format_performance_summary` добавляет короткие нейтральные строки для обеих команд к сообщению загрузки. Бот не выбирает «нашу команду» и не передаёт самодельные confirmed-роли.

Ошибка анализа не превращает успешное сохранение матча в ошибку загрузки: пользователю сообщается, что анализ недоступен. Лог содержит только match_id и тип исключения. 404/429/unavailable не запускают evaluator. Telegram-сообщение по-прежнему отправляется тем же обработчиком в ту же группу; реальные отправки в рамках проверки не выполнялись.

Сервис доступен для повторного использования будущим REST-обработчиком без копирования формул. Новый REST endpoint, хранение performance report, UI и рекомендации альтернативных героев в этом задании не создавались.
