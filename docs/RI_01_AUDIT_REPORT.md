## B. Архитектура вычислений

Путь данных: OpenDota `/matches/{id}` → валидация и санитарная копия ответа → PostgreSQL TTL-кэш raw snapshot → `normalize_match_snapshot` → `analyze_performance` → отдельный сохранённый `RuinerReport` → read-only REST. Бот получает короткую сводку общего процесса; GET только читает готовый отчёт и не вызывает OpenDota или evaluator.

Алгоритм создаёт `PlayerPerformance` для каждого **имеющегося** участника, максимум 10. Он не дополняет отсутствующих игроков. Сортирует по `player_slot`, затем сравнивает игрока только с доступными союзниками его команды и ролевой группы. Победитель, противники, патч, драфт и Match ID не входят в формулу. Командный счёт нужен лишь для доли участия; длительность — для скоростей и минимального порога.

Версия в ответе — `ruiner_v1`; `config_digest` — SHA-256 сериализованной конфигурации. Для обоих воспроизведённых снимков: `31147c647698fe40a5109d8520227d2e62f5d203aa5299a5585e3c1f5c6779a8`. Версия хранилища секции — `group_flow_v1:ruiner`, отдельно от версии формулы.

## C. Формула и таблица коэффициентов

Пусть `x` — наблюдение игрока, `b` — медиана **других** доступных игроков его команды/группы, `u` — минимальная единица знаменателя. Для абсолютных чисел `u=1`, для величин в минуту `u=60/duration`, для участия `u=1/team_score`. `d=max(b,u)`; `clamp(z)=min(1,max(0,z))`.

- Для смертности: `bad=clamp((x-b)/d)`, `good=clamp((b-x)/d)`.
- Для остальных метрик: `bad=clamp((b-x)/d)`, `good=clamp((x-b)/d)`.
- При `b=0` для метрики «больше лучше» численное сравнение не проводится; `x>0` даёт только описательный `observed_contribution`.
- При отсутствии хотя бы одного peer с известным значением сравнение недоступно (`minimum_cohort=2`, включая игрока). Сигнал попадает в список только при величине ≥0,20; меньшие ненулевые величины всё равно участвуют в численном индексе.

| Метрика | Игровой смысл, источник OpenDota → наблюдение | Вклад / знак | Null и реальный 0 |
| --- | --- | --- | --- |
| Смертность | `deaths` → `deaths/(duration/60)` | Отрицательная ось survival: 0,30 core; 0,50 support/unknown. Избыток смертей повышает индекс. | Null при отсутствии deaths/duration, коротком/неизвестном матче или если суммарно у команды <5 известных смертей. 0 смертей — корректное наблюдение, `u` защищает от нулевой медианы. |
| Участие в убийствах | `kills`, `assists`, `radiant_score/dire_score` → `(K+A)/team_score` | Отрицательная ось participation: 0,25 core; 0,50 support/unknown. Недостаток повышает индекс. | Null при неизвестном K/A, `team_score<10` или `K+A>team_score`; доля не обрезается до 1. Нулевое участие при счёте ≥10 — корректный 0. |
| GPM, XPM | `gold_per_min`, `xp_per_min` → как есть | Core: economy = среднее двух дефицитов, общий вес 0,25 (по 0,125 до перенормировки). Support/unknown не штрафуются. | Для economy нужны **оба** поля; отсутствие одного делает всю ось null. Реальный 0 может дать дефицит; нулевая медиана отключает сравнение. |
| Урон героям | `hero_damage` → `hero_damage/(duration/60)` | Core: отрицательная ось impact, вес 0,20. Support/unknown: только возможный положительный credit. | Отсутствие/нулевой baseline отключает численное сравнение; реальный 0 на фоне положительного baseline может дать дефицит core, у остальных штрафа нет. |
| Урон строениям | `tower_damage` → в минуту | Только положительный credit, не обязательный урон. | Null не штрафуется; 0 не даёт credit. |
| Лечение | `hero_healing` → в минуту | Только положительный credit; нет штрафа за отсутствие лечения. | Null не штрафуется; 0 при нулевой медиане не даёт credit. |
| Установленные wards | `obs_placed`, `sen_placed` → соответствующие счётчики | Каждый — только кандидат на положительный credit. | Null не превращается в 0; реальный 0 не даёт credit. |
| Уничтоженные wards | `observer_kills`, `sentry_kills` → соответствующие счётчики | Каждый — только кандидат на положительный credit. | То же. |
| KDA | `(kills+assists)/deaths` | Вес 0: только описательная метрика, чтобы не дублировать смерти/участие. | Null при отсутствующих K/A/deaths или `deaths=0`; 0 при K+A=0 и deaths>0. |

Для core: `axes={survival, participation, economy, impact}`, веса `{0,30; 0,25; 0,25; 0,20}`. Для support и unknown: `{survival, participation}`, веса `{0,50; 0,50}`. Положительный credit равен `15 × max(good_m)` по доступным необязательным метрикам (для support/unknown также hero damage), максимум 15. Несколько вкладов не суммируются.

`coverage = Σ весов доступных осей`. Если доступных осей <2 либо `coverage<0,70`, `error_index=null`. Иначе:

```text
burden = 100 × Σ(вес_оси × bad_оси) / coverage
error_index = floor(max(0, burden − positive_credit) + 0.5)
```

Ось ограничена [0,1], кредит неотрицателен; шкала индекса — целые 0–100, **больше означает больше относительных отрицательных сигналов**. Это не вероятность виновности. Веса, пороги 900 секунд, 10 командных убийств, coverage 0,70, selection 70/15 и credit 15 документированы как **гипотезы дизайна**, а не обученные коэффициенты или проверенные игровые нормы. Документированная причина исключения KDA — недопущение двойного штрафа; причина отсутствия штрафа за healing/wards — нет универсального обязательного минимума. Статистического обоснования конкретных чисел в репозитории нет.

## D. Источники и качество входных данных

Нормализатор принимает только неотрицательные целые K/D/A, GPM/XPM, damage, healing, wards; невалидное и отсутствующее значение становится null. `position_est` становится estimated, `lane_role` описывает линию и **не** подтверждает фармовую позицию. Патч читается, но алгоритм его не учитывает. Поддерживаемые `game_mode`: 1, 2, 22; другие режимы и длительность <900 секунд дают null для всех индексов. Команда должна иметь ровно пять игроков, уникальные известные hero ID и согласованные со стороной слоты. Для survival нужны известные смерти всех пяти и сумма ≥5.

`FOUND_FULL` у ingestion означает присутствие набора полей **уровня матча** (`FULL_FIELDS`), а не полноту всех полей каждого игрока. Даже при нём wards, позиции или damage могут отсутствовать. `evidence_coverage` покрывает только взвешенные отрицательные оси, а не необязательные credit-метрики; поэтому coverage=1 не означает полный OpenDota parse.

Не используются `last_hits`, `net_worth`, уровень, stuns, buybacks, события Timeline, рейтинг, тип героя и показатели противников. В нормализованной модели нет `leaver_status`; специальной обработки leaver в расчёте нет.

## E. Ролевые поправки

Позиции 1–3 → core, 4–5 → support, null → unknown. Core сравнивается только с core той же команды, support — только с support, unknown — со **всеми** союзниками и использует fallback 50/50. Вариант estimated тоже выбирает группу/веса, но всегда имеет low confidence; это создаёт риск, если оценка роли из фарма ошибочна. Повтор одной позиции у игроков команды сбрасывает всю команду в unknown и добавляет `conflicting_positions`.

Medium confidence требует численный индекс, coverage≈1, confirmed-позицию игрока и confirmed-позиции всей сравниваемой группы. Обычный pipeline не передаёт `positions` и получает из OpenDota только estimated/unknown, поэтому для обычного отчёта уверенный выбор практически недостижим. `summary.data_quality.roles` по линии не повышает уверенность Ruiner.

## F. Логика выбора кандидата

Команды выбираются **отдельно**. `select_team` сначала требует всех пяти игроков с индексом, `confidence=medium`, `coverage=1`. Затем сортирует по индексу (при равенстве по слоту), требует верхний индекс ≥70, отрыв от второго ≥15 и не менее двух осей верхнего игрока с deficit ≥0,20. Нарушение каждого условия даёт `no_confident_selection` с кодом причины; нулевая/низкая уверенность команды даёт `incomplete_or_low_confidence_team`.

Общий `summary` без явно переданного доверенного `selected_team` всегда `no_confident_selection` с `team_context_not_provided`, даже если внутри одной команды выбран кандидат. Текущий основной pipeline `selected_team` не передаёт. Ни победа/поражение, ни герой не выбирают команду и не меняют индекс. Leaver никак специально не обрабатывается.

## I. Выявленные дефекты и потенциальные риски

1. **Подтверждённый дефект документации:** `RUINER_ANALYZER_SPEC.md` и `STAGE2_07_REPORT.md` описывают отсутствие REST endpoint и сохранения; актуальный `match_analysis.py` сохраняет отчёт, `matches.py` его отдаёт. Это не изменение формулы.
2. **Подтверждённый пробел проверки качества данных:** `8888765469.json` содержит 25 суммарных убийств Dire при `dire_score=20`. Нормализатор и evaluator принимают fixture, поскольку проверяют только `K+A≤team_score` по отдельному игроку, но не суммарную согласованность команды. В приведённом случае индекс Dire всё равно 0; влияние на другие входы не проверено. Нужна отдельная политика валидации, без изменения расчёта в RI-01.
3. **Подтверждённое отсутствие leaver-контекста:** `leaver_status` не переносится в `PlayerStat`; сопоставление leaver с полным составом может быть ошибочно истолковано. Тест отсутствует.
4. **Риск интерпретации:** средняя уверенность означает полноту отрицательных осей и подтверждённые роли, а не доказанную причинность и не наличие необязательных вкладов. При обычных estimated/unknown ролях выбор игрока фактически заблокирован.
5. **Риск малой выборки и patch/hero-слепоты:** медиана 1–4 peers не является игровой нормой; патч и способности героев не учитываются. Одинаково слабые игроки дадут нулевые относительные отклонения. Численного дефекта формулы на проверенных случаях не обнаружено.

## J. Технический долг и отсутствующие данные

Для обоснованной уверенной командной селекции отсутствует подтверждённый источник позиций 1–5 в обычном pipeline. Нет калибровки весов/порогов на размеченной выборке по патчам, героям, ролям и рейтингу; нет входа leaver-статуса, контекста смертей, назначения/результата wards, целей, доступности фарма и временных игровых фаз. Проекция 9051271323 не содержит GPM/damage/healing/wards, поэтому не позволяет оценить влияние core economy/impact и credit. Независимая fixture содержит эти totals, но не реальные игровые наблюдения. Полные live OpenDota ответы в RI-01 не запрашивались.

## K. Рекомендации без реализации и границы вывода

- **Подтверждено кодом:** текущая формула и веса; отдельное сравнение команд; nullable оси; отсутствие winner/draft/leaver в формуле; сохраняемый REST-отчёт; низкая уверенность при неподтверждённых ролях.
- **Подтверждено тестами и replay:** 57/57 существующих тестов, 20/20 независимых арифметических пересчётов, точное повторение сохранённого отчёта 9051271323; сценарии support/core, нулевые и отсутствующие значения, смена победителя, повтор.
- **Не подтверждено:** статистическая валидность коэффициентов, причинная связь индекса с поражением, корректность поведения при leaver, полный live Telegram/OpenDota прогон в рамках этого аудита.
- **Обнаружен дефект:** устаревшие утверждения документации об API/хранении и недостаточная проверка межигроковой согласованности team kills на синтетической fixture; численный дефект функции `error_index` на проверенных данных не установлен.
- **Требуется продуктовое решение:** должен ли индекс выделять кандидата без confirmed-позиций; как учитывать leaver и невалидный командный счёт; какие внешние данные и критерий качества нужны для калибровки. До такого решения не объявлять численные значения доказательством ошибки игрока.

Рекомендуемый следующий шаг — отдельно согласовать эти правила и набор реалистичных размеченных матчей, затем ставить задачу на изменения. В RI-01 ничего не исправлялось.
