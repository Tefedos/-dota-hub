## Предлагаемая архитектура

```text
Telegram WebView → React / TypeScript → FastAPI → PostgreSQL
Telegram group → aiogram polling → OpenDota → PostgreSQL
```

Модульный монолит: один frontend и один backend. Стек по требованиям: Python 3.12+, FastAPI, Pydantic v2, React, TypeScript, Vite, PostgreSQL, SQLAlchemy 2.x, Alembic. Redis, очереди, микросервисы и ML/LLM не требуются.

- React отвечает за отображение, навигацию и состояния запросов. Согласованное направление оформления: мобильный dark UI, графитово-синий фон, фиолетовые акценты, красные предупреждения и зелёные успехи. Конкретные токены и компоненты пока не предоставлены.
- FastAPI отвечает за контракт HTTP, валидацию, ошибки и доступ к данным. Авторизация и обработка матчей добавляются позднее.
- PostgreSQL хранит данные приложения; SQLAlchemy описывает модели, Alembic управляет изменениями схемы. Не создавать параллельную базу, если у существующего приложения уже есть подходящая.
- OpenDota доступен только backend bot-процессу; браузер не получает API-ключ и не обращается к провайдеру напрямую.
- Telegram initData проверяется сервером по официальной HMAC-схеме; signature входит в подписываемые поля. Frontend не считается доверенным источником личности. Не делать временный вход по переданному user ID.

## Реализованный API-контракт инкремента 02

Предлагаемый канонический путь: `GET /api/v1/health`. Общий план использует `/api/v1/healthz`, но текущее задание явно требует `/api/v1/health`; принимаем его для этапа 1. Существующих клиентов в этой папке не обнаружено. Совместимость внешних клиентов требует проверки после получения исходного приложения.

- Доступ без авторизации, параметров и тела запроса.
- Успех: HTTP 200, `Content-Type: application/json`.
- Тело строго: `{"status":"ok","service":"dota-hub-api"}`.
- Значение `status` — литерал `ok`, `service` — литерал `dota-hub-api`.
- Endpoint проверяет, что API обслуживает запросы; не обращается к БД, Telegram или OpenDota. Ответ 200 не является проверкой готовности БД.
- Не раскрывает версии библиотек, секреты и внутренние настройки; ответ не кэшируется (`Cache-Control: no-store`).

Общий формат ошибок собственного API:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Ресурс не найден",
    "details": []
  }
}
```

`code` — стабильный машинный код, `message` — безопасный текст, `details` — массив объектов `{ "field": "...", "message": "..." }` без исходных пользовательских значений и секретов. Для 404 используется `NOT_FOUND`, для 405 — `METHOD_NOT_ALLOWED`, для 422 — `VALIDATION_ERROR`, для 500 — `INTERNAL_ERROR`. В 500 клиент не получает traceback и текст внутреннего исключения. У health нет входных полей, поэтому 422 описывает общую конвенцию API, а не ожидаемый сценарий этого endpoint. В инкременте 03 добавлен GET /api/v1/health/db: SELECT 1, HTTP 200 с {"status":"ok","database":"available"} или безопасный 503 с error.code=DATABASE_UNAVAILABLE. Liveness остаётся независимым от БД.

## Реализованная схема инкремента 03

Третий промпт уточнил общий план: созданы **четыре** таблицы вместо предварительного варианта из трёх.

- `telegram_users`: telegram_user_id BIGINT PK, nullable username/display_name, created_at/updated_at TIMESTAMPTZ.
- `matches`: match_id BIGINT PK, fetch_status (pending/ready/unavailable/failed), nullable raw_payload JSONB/fetched_at, created_at/updated_at TIMESTAMPTZ.
- `match_analyses`: UUID PK, match_id FK → matches RESTRICT, algorithm_version VARCHAR(64), status (pending/ready/failed), nullable report_payload JSONB/completeness/computed_at, created_at; UNIQUE(match_id, algorithm_version) и индекс match_id.
- `user_match_history`: UUID PK, telegram_user_id FK → telegram_users RESTRICT, match_id FK → matches RESTRICT, last_viewed_at; UNIQUE(telegram_user_id, match_id), индексы (telegram_user_id, last_viewed_at DESC) и match_id.

Идентификаторы пользователей/матчей положительные; UUID создаёт PostgreSQL. Время с timezone, сессии используют UTC; входные timestamps без timezone отклоняются. Внешние bigint ID в будущих JSON API должны оставаться строками. Допустимые значения completeness — full/partial/missing или NULL. Служебная alembic_version хранит 0001_initial.

Один async engine/session factory на lifespan, сессия на запрос, явные транзакции в вызывающем коде. Закрытие сессии откатывает незакоммиченную работу; shutdown освобождает pool. Таблицы не создаются при старте приложения. Repository-функции используют ON CONFLICT, не делают commit и не публикуются в пользовательском API. VerifiedTelegramUser — внутренний тип, который auth-сервис создаёт только после проверки подписи; сам тип не проверяет Telegram.

История связана с матчом, а не с версией анализа. Позднее событие просмотра не уменьшает last_viewed_at. Повторное сохранение той же версии анализа сохраняет её UUID; новая версия хранится отдельно. ON DELETE RESTRICT предотвращает каскадное удаление. updated_at поддерживается ORM/repositories, триггер для внешнего SQL не добавлен.

DATABASE_URL хранится в backend/.env (Git ignored, 0600), Settings использует SecretStr. Compose считывает тот же env; POSTGRES-переменные предназначены только для локальной инициализации. Пароль сгенерирован локально и не выводился. Для авторизации нужны BOT_TOKEN и отдельный SESSION_SECRET только в backend; для unit-тестов используются сгенерированные в памяти секреты, реальные секреты не нужны.

Тесты работают на настоящем PostgreSQL, с отдельными базами и откатом транзакций. Начальный downgrade допускается только с явным флагом на пустой loopback-БД dota_hub_migration_test. Реальный цикл upgrade → повторный upgrade → downgrade → upgrade и alembic check прошёл; изменение существующей dev/prod-схемы разрушительными командами не выполнялось. Тестовая запись сохранности пережила перезапуск и находится только в dota_hub_test; dev-таблицы пусты.
